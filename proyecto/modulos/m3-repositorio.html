Todo el proyecto vive en un repositorio privado de GitHub, uno por equipo: la ficha, el preregistro, las descargas, el código que une y analiza, los mapas y el informe. No se entrega nada por otro lado. El repositorio es a la vez el canal de entrega y la documentación del caso: quien lo abra tiene que poder entender qué hiciste y reproducirlo sin preguntarte nada.

Crearlo, antes de la ficha

  1. Créalo privado, con el nombre @@NOMBRE_REPO@@ —tu apellido, o los de los dos— y con un README.md. Si es un proyecto conjunto, el nombre es otro, y lo dice el módulo 8 de la guía de Series.
  2. En pareja, quien lo crea invita al otro como colaborador, y cada uno trabaja con su propia cuenta: el historial dice quién hizo qué.
  3. Invita al docente como colaborador: el usuario @@USUARIO_DOCENTE@@, en Settings → Collaborators → Add people. Sin esa invitación el docente no ve tu repositorio, y lo que no se ve no está entregado.

Es privado a propósito: los otros equipos no ven tu trabajo. La ficha es la primera entrega, así que el repositorio tiene que existir, con el docente invitado, antes del @@FICHA_CIERRA@@.

Cómo se organiza

Usa esta estructura: es la que espera la plantilla del informe y la que el docente va a buscar. Abre la carpeta como proyecto de RStudio, con su archivo .Rproj, y todas las rutas quedan relativas a la raíz.

Las buenas prácticas

Las cuatro primeras entran en la rúbrica, en el criterio de reproducibilidad del informe; las demás son las que hacen que las cuatro primeras se cumplan sin esfuerzo.

  • El README es la puerta. Dice qué se pregunta, quiénes son, de dónde sale cada archivo de datos/crudos/ —la fuente, el enlace y la fecha de descarga— y cómo se reproduce el informe, paso a paso. Alguien que no te conoce tiene que poder clonar el repositorio, seguir el README y obtener tu informe.
  • Los datos crudos no se tocan a mano. Lo que hay en datos/crudos/ es lo que se descargó. Si hay que corregir algo —un código DIVIPOLA mal escrito, un municipio que cambió de nombre—, se corrige en R/datos.R y se anota: así se ve qué cambió y por qué.
  • Lo exploratorio va aparte, marcado como tal, como explica el módulo del preregistro.
  • Rutas relativas. Nada de C:/Users/...: con el proyecto de RStudio abierto, los datos son "datos/unidades.gpkg" en cualquier computador.
  • Commits pequeños, con un mensaje que diga qué cambió. «Une la tasa con los municipios por DIVIPOLA» sirve; «cambios» o «final final», no. Lo que fecha el preregistro no son las fechas de los commits, que las pone tu computador, sino la hora en que GitHub publicó su release.
  • Una geometría pesada se recorta. GitHub no acepta archivos de más de 100 MB. Si la capa nacional pesa demasiado, guarda en datos/crudos/ solo tu territorio y deja en el README el enlace a la capa completa y el código que la recorta.
  • Lo que R genera solo no se sube: .Rhistory, .RData y .Rproj.user/ van en el .gitignore. La excepción es el informe renderizado, que sí se sube: es lo que se lee sin instalar nada.

Cómo se entrega: una release por hito

Hacer commits no es entregar. Cada hito se entrega publicando una release del repositorio con su etiqueta: @@ETIQUETAS@@. En GitHub es Releases → Draft a new release: escribes la etiqueta, eliges Create new tag y pulsas Publish release. Antes, haz Push: la release toma lo que está en GitHub, no lo que tienes en tu computador, y un commit que no subiste no está entregado.

La hora de la entrega es la hora en que GitHub publica la release, no la de tus commits, y tiene que ser antes de las @@HORA_ENTREGA@@ del día de cierre. Si después sigues haciendo commits, la release no cambia: lo entregado es lo que había en GitHub en ese momento. Si antes del cierre ves un error, lo corriges y publicas otra release con un número, como @@ETIQUETA_PREREGISTRO@@-2: se califica la última que llegó a tiempo. Si no llegó ninguna a tiempo, se califica la primera que llegó, con el descuento por entrega tardía que explica el primer módulo.

La release congela el preregistro. Después de publicar la release @@ETIQUETA_PREREGISTRO@@, el archivo preregistro.md no se vuelve a editar: si algo cambia —la W principal deja islas que no esperabas, una fuente cambió—, va como desviación en el avance. Tampoco se mueve su etiqueta ni se borra la release para volver a crearla: una etiqueta se puede cambiar de commit, y hacerlo después del cierre es reescribir lo entregado.
